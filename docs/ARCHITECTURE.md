# Архитектура «Аким на 5 часов»

Итог обсуждения Claude и Codex. **Статус: ждёт утверждения владельцем.** До утверждения код по этому плану
не пишется, коммитов и пушей нет. Задача, данные и формула — [TZ.md](TZ.md).

## Принципы

- **Score считает только детерминированный движок** строго по формуле ТЗ. ИИ объясняет результат, сравнивает
  сценарии и ищет улучшения через инструменты движка — числа он не считает и не придумывает.
- **Сервер не доверяет клиенту:** любой набор решений, пришедший в любой эндпоинт, заново валидируется и пересчитывается.
- **Всё работает без ключа OpenAI** (`LLM_MOCK=true` или ключа нет): движок, оптимизатор, шаблонный аналитик,
  детерминированный советник. Так проект воспроизводится с чистого checkout.
- **Официальная модель ТЗ не меняется.** Всё, что выходит за неё (события, перцентиль), — вне MVP.

## Данные

- `docs/dataset.json` — официальный источник, перенесён из ТЗ без изменений.
- `backend/app/data/dataset.json` — копия для runtime: деплой возит на сервер только `backend/app`.
  Тест проверяет, что копия совпадает с официальным источником. Деплой не меняем.
- `get_dataset()` — pydantic-модель, неизменяемая, загружается один раз.

## Ядро симуляции — `backend/app/sim/` (Claude)

Интерфейс, на который опираются оптимизатор, ИИ-слой и API:

| Функция | Что делает |
|---|---|
| `get_dataset() -> Dataset` | данные кейса |
| `Decision{measure_id, district_id \| None}` | одно решение |
| `validate(decisions) -> list[Violation]` | **все** нарушения сразу: `code`, `message` (по-русски), `measure_ids`, `district_id` |
| `evaluate(decisions) -> EvalResult` | `{valid: false, violations}` без Score **или** `{valid: true, result: ScenarioResult}` |
| `score_subset(decisions) -> float` | быстрый путь без валидации, любой поднабор 0–5 мер — для оптимизатора и Shapley |

`ScenarioResult`: `cost`, `remaining`, `score`, `base_score`, `delta`;
`components{d_avg, min_d, min_district_id, n_crit, critical[{district_id, indicator, value}]}`;
`districts[{id, before, after, delta, d_before, d_after}]`;
`measures[{measure_id, district_id, cost, share, effects[{district_id, indicator, value}], shapley}]`;
`synergies[{pair, district_id, indicator, bonus}]`.

**Расчёт** (раздел 3 ТЗ): эффект меры × (8 − L)/8 по её районам; синергия — фиксированный бонус в районе первой меры
пары, только если обе меры выбраны; `clip(0, 100)` **один раз** после общей суммы эффектов и синергий;
`D_d = Σ w_k × I'_dk`; `D_avg` — средневзвешенное по населению; `N_crit` — пары со значением **строго** меньше 40;
`Score = 0.7 × D_avg + 0.3 × min(D_d) − N_crit`. В ядре ничего не округляется, округляет только UI.

**Валидатор** — все 8 правил ТЗ плюс неизвестные ID. Коды: `count`, `duplicate`, `unknown_measure`, `unknown_district`,
`district_required`, `district_forbidden`, `direction_limit`, `incompatible`, `budget`. Порядок решений не важен.
Каждое направление выбирать не обязательно: до 2 мер из одного направления.

**Вклад мер:**
- прямые эффекты — что каждая мера изменила в показателях районов с учётом лага;
- точное значение Шепли по 5 мерам (32 поднабора через `score_subset`) — вклад меры в итоговый Score.
  Учитывает синергии, минимум и штрафы, вклады складываются: **Σ вкладов = Score − база**.

Эталонные числа: база **52.55768** (52.56), пример из ТЗ **56.54307** (56.54).

## Оптимизатор — `backend/app/sim/optimize.py` (Codex)

- Точный полный перебор: 1181 допустимый набор мер, 694 395 сценариев с районами. Только stdlib, отсечения по
  бюджету и правилам, заранее посчитанные вклады мер.
- Ограничения: обязательные и исключённые меры, зафиксированные решения, лимит стоимости.
- Кеш результатов. Прогрев — фоновой задачей при старте (`asyncio.to_thread`), старт сервера не блокирует.
- «Точный оптимум» ставится только после полного перебора; при срабатывании дедлайна ложной гарантии нет.
  Если допустимых сценариев под ограничения нет — явный ответ без рекомендации.
- Для сотен тысяч сценариев не храним все 50 показателей: только кандидатов и кеш итоговых баллов.
- NumPy — только если замер покажет, что stdlib не успевает, и после согласования с владельцем.

## ИИ-слой — `backend/app/llm.py`, `sse.py`, `ai/` (Codex)

**SSE.** Одна обёртка на все долгие операции. События: `delta`, `tool_call`, `tool_result`, `result`, `done`,
`error`, `ping` (heartbeat раз в 15 с). Первое событие — сразу статус. Чат остаётся совместимым (`delta`/`done`/`error`).

**Аналитик** — `POST /api/ai/analyze` (SSE):
- принимает решения, сервер сам их считает и строит факты с `fact_id`;
- модель возвращает structured output `{summary, strengths[], risks[], consequences[], tradeoffs[], recommendations[]}`,
  в каждом пункте текст и ссылки `fact_ids` / `measure_ids` / `district_ids`;
- проверки: в тексте модели нет цифр, все ссылки принадлежат текущему результату. Нарушение — одна перегенерация,
  затем пункт берётся из шаблона. Отсутствие цифр не доказывает, что текст верен, поэтому числа рядом с пунктом
  UI показывает из фактов по `fact_ids`;
- любое предложенное действие снова проходит `evaluate`;
- без ключа — шаблонный аналитик по тем же фактам и той же схеме, в интерфейсе помечен «шаблонный».
  Сбои провайдера не прячем: `LLMError` уходит в интерфейс.

**Советник** — `POST /api/ai/advise` (SSE):
- настоящий вызов инструментов OpenAI (function calling), инструменты `evaluate`, `optimize`, `improve` (лучшая замена 1–2 мер);
- модель сама выбирает инструменты под цель пользователя на естественном языке («сохрани школу в Нуре»);
- лимиты: до 6 вызовов инструментов, ограничение шагов модели, общий дедлайн;
- в интерфейсе вызовы видны кратко: инструмент, аргументы, итог. Ход рассуждений модели не показываем;
- итоговый набор сервер перевалидирует и пересчитывает. Применяется только кнопкой пользователя;
- без ключа — детерминированный план на тех же инструментах и шаблонное объяснение.

**Оптимум** — `POST /api/ai/optimize` (SSE): сразу статус, heartbeat, затем результат и признак точности.

## API

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/api/sim/config` | датасет и расчёт базы |
| POST | `/api/sim/evaluate` | `{valid: false, violations}` или `{valid: true, result}`; битый JSON или схема — 422 |
| POST | `/api/ai/analyze` | SSE, объяснение сценария |
| POST | `/api/ai/advise` | SSE, вызовы инструментов и предложение |
| POST | `/api/ai/optimize` | SSE, оптимум с ограничениями |

Контракт: pydantic → OpenAPI → TypeScript-типы для фронта. `/api/sim/*` в `routes/sim.py`, `/api/ai/*` в `routes/ai.py`.

## Фронтенд (участник команды, назначает владелец)

Один основной экран:
- районы «было/стало» (5 районов × 10 показателей);
- 5 слотов решений, шкала бюджета;
- каталог мер с подсказками по синергиям и несовместимостям;
- итог: Score, его составляющие, вклады мер, объяснение ИИ;
- сравнение с предложением советника и кнопка «Применить».

База показывается отдельно. У невалидного черновика Score нет, вместо него причины. Все 5 направлений видны,
выбирать каждое не обязательно. Работает от 360 px. Макет и прототип на контракте — сразу после фиксации API, не в конце.

## Тесты (всё без сети)

- **Ядро:** 8 правил и неизвестные ID; перестановка решений; меры «город» и «район»; все синергии и несовместимости;
  M11 с отрицательным T1; clip после общей суммы; порог 40 и «строго меньше 40»; min и штраф за каждую пару;
  Σ Шепли = delta; неизменность датасета и входных данных; числа 52.55768 и 56.54307; копия датасета совпадает с официальной.
- **Оптимизатор:** все результаты валидны; ограничения соблюдены; сверка с полным перебором на маленькой фикстуре.
- **ИИ с фейковым LLM:** неверные аргументы, неизвестный инструмент, лимиты, ошибки провайдера, повторная проверка финала.

## Воспроизводимость и README

  пошаговый сценарий проверки с ожидаемыми числами (база 52.56 → пример 56.54 → оптимум).
- Docker вне MVP. Предлагается владельцу как опция после MVP.

## Демо (3 минуты)

1. База: Score 52.56 и два провала Нуры (S1, S2 ниже 40).
2. Невалидный набор — конкретная причина от валидатора.
3. Пример из ТЗ: 95 единиц, Score 56.54, сработавшая синергия M10 + M12, вклады мер.
4. Советнику: «сохрани школу в Нуре» → видимые вызовы инструментов → сравнение с текущим набором до применения.
5. «Применить» → новый Score.

## Порядок работ

1. Владелец утверждает план, назначает участников на фронт и демо и решает, заливать ли локальный каркас
   в репозиторий команды: сейчас в нём только стартовый README от организаторов, каркас лежит локально без `.git`.
   После этого — проверяем актуальный checkout, все новые изменения идут в рабочих ветках и через PR.
2. Claude — ядро, тесты, схемы API. Параллельно Codex — SSE-обёртка и цикл вызова инструментов (от ядра не зависят).
3. Фронт — макет и прототип на контракте с тестовыми данными.
4. Codex — оптимизатор и советник на интерфейсе ядра, затем аналитик и шаблонные fallback.
5. Claude — README со сценарием проверки, ревью Codex.

Перед каждым PR: `pytest`, `ruff`, `pnpm lint`, `pnpm build` из AGENTS.md и ручной прогон сценария в браузере.
Без новых зависимостей и изменений деплоя без согласования.
